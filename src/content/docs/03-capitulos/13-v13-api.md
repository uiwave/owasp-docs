Hoy la mayoría de las aplicaciones son **interfaces de sus propias APIs**: la web llama a la API, la app móvil llama a la API, otros servicios llaman a la API. Cada llamada es una puerta más que cuidar.

> **Objetivo de control:** una aplicación verificada que usa APIs de capa de servicio de confianza (normalmente JSON, XML o GraphQL) tiene:
>
> - **Autenticación, gestión de sesiones y autorización adecuadas** en todos los servicios web.
> - **Validación de entrada** de todos los parámetros que transitan de un nivel de confianza inferior a superior.
> - **Controles de seguridad eficaces** para todos los tipos de API, incluida la nube y las Serverless APIs.
>
> *Lea este capítulo en combinación con los demás capítulos del mismo nivel: ya no se duplican los problemas de autenticación o administración de sesiones de API.*

## V13.1 Seguridad Genérica de Servicios Web

### 13.1.1 — Mismos codificadores y analizadores en toda la app (CWE-116)

> *"Verifique que todos los componentes de la aplicación utilizan las mismas codificaciones y analizadores para evitar el análisis de ataques que explotan un comportamiento de análisis de archivos o URI diferente que se podría usar en ataques SSRF y RFI."*

**Explicación:** si cada componente interpreta las URLs a su manera, el atacante explota las diferencias (parsing confusion): el front filtra `http://malicioso.com` pero el backend normaliza y sigue a `http://localhost`. Una única forma de parsear en todas partes. **Niveles: L1, L2, L3.**

### 13.1.2 — [ELIMINADO, DUPLICADO DE 4.3.1]

Requisito eliminado en v4.0.3 por duplicado con el 4.3.1 (MFA en interfaces administrativas).

### 13.1.3 — Las URLs de la API no exponen información confidencial (CWE-598)

> *"Verifique que las direcciones URL de la API no exponen información confidencial, como API keys, los tokens de sesión, etc."*

**Explicación:** las URLs van a logs, historiales y cabeceras Referer: una API key en la URL se filtra a terceros. Los secretos van en encabezados o cuerpos. **Niveles: L1, L2, L3.**

### 13.1.4 — Autorización en múltiples capas (CWE-285)

> *"Verifique que las decisiones de autorización se toman en el URI, se aplican mediante seguridad programática o declarativa en el controlador o enrutador, y en el nivel de recursos, se aplican mediante permisos basados en modelos."*

**Explicación:** la defensa en profundidad: control en la ruta, en el controlador y en el modelo de datos. Si una capa falla, la otra detiene al atacante. **Niveles: L1, L2.**

### 13.1.5 — Rechazar tipos de contenido inesperados (CWE-434)

> *"Verifique que las solicitudes que contienen tipos de contenido inesperados o contenido que falta se rechazan con encabezados adecuados (estado de respuesta HTTP 406 Inaceptable o 415 Tipo de medio no compatible)."*

**Explicación:** si esperas JSON y llega `text/html` (o nada), rechaza con el código adecuado: el tipo de contenido inesperado es la firma de un ataque o de un parser confusion. **Niveles: L1, L2.**

## V13.2 Servicio Web RESTful

> *Nota sobre validación de esquema JSON:* se encuentra en una etapa preliminar de estandarización. Al usarla, combine estas estrategias: análisis del objeto JSON (elementos faltantes o adicionales), validación de valores (tipo, formato, longitud) y validación formal del esquema JSON. Supervise las bibliotecas de validación, que se actualizan periódicamente hasta que el estándar se formalice.

### 13.2.1 — Métodos HTTP válidos para la acción (CWE-650)

> *"Verifique que los métodos HTTP RESTful habilitados son una opción válida para el usuario o la acción, como impedir que los usuarios normales usen DELETE o PUT en recursos o API protegidos."*

**Explicación:** un usuario normal no borra recursos: `DELETE /pedidos/100` debe responder "prohibido", no ejecutarse. Cada método está habilitado solo donde corresponde. **Niveles: L1, L2, L3.**

### 13.2.2 — Validación de esquema JSON antes de aceptar (CWE-20)

> *"Verifique que la validación del esquema JSON está en su lugar y se comprueba antes de aceptar la entrada."*

**Explicación:** el contrato del API se cumple: antes de procesar, se valida que el JSON cumple el esquema (campos, tipos, obligatoriedad). Lo que no cumple, se rechaza. **Niveles: L1, L2, L3.**

### 13.2.3 — Protección CSRF en APIs con cookies (CWE-352)

> *"Verifique que los servicios web RESTful que utilizan cookies están protegidos contra la falsificación de solicitudes entre sitios, mediante el uso de una o más de las siguientes formas: patrón de cookies de doble envío, 'nonces' CSRF o comprobaciones de encabezado de solicitud de origen."*

**Explicación:** si la API autentica con cookies, otro sitio puede hacer que el navegador de la víctima llame a la API (CSRF). Doble envío de cookies, nonces CSRF o verificación de origen lo impiden. **Niveles: L1, L2, L3.**

### 13.2.4 — [ELIMINADO, DUPLICADO DE 11.1.4]

Requisito eliminado en v4.0.3 por duplicado con el 11.1.4 (controles anti-automatización).

### 13.2.5 — Verificar el tipo de contenido entrante (CWE-436)

> *"Verifique que los servicios REST comprueben explícitamente que el tipo de contenido entrante sea el esperado, como application/xml o application/json."*

**Explicación:** "envíame JSON" significa `Content-Type: application/json` real: se verifica explícitamente para evitar que un payload XML o HTML engañe al parser. **Niveles: L1, L2.**

### 13.2.6 — Encabezados y payload confiables en tránsito (CWE-345)

> *"Verifique que los encabezados de mensaje y la carga útil (payload) son confiables y no se modifican en tránsito. Requerir un cifrado seguro para el transporte (solo TLS) puede ser suficiente en muchos casos, ya que proporciona confidencialidad y protección de integridad. Las firmas digitales por cada mensaje pueden proporcionar una garantía adicional sobre las protecciones de transporte para aplicaciones de alta seguridad, pero conllevan complejidad y riesgos adicionales para compensar los beneficios."*

**Explicación:** nadie debe poder modificar la petición en el camino: TLS lo garantiza en el transporte; para aplicaciones de alta seguridad, firmas digitales por mensaje añaden protección extra (con su costo de complejidad). **Niveles: L1, L2.**

## V13.3 Servicio Web SOAP

### 13.3.1 — Validación XSD antes de procesar (CWE-20)

> *"Verifique que la validación del esquema XSD tiene lugar para garantizar un documento XML formado correctamente, seguido de la validación de cada campo de entrada antes de que se realice cualquier procesamiento de esos datos."*

**Explicación:** el XML se valida contra su esquema (XSD) y cada campo se valida **antes** de procesarlo: la estructura correcta es la condición previa del procesamiento. **Niveles: L1, L2, L3.**

### 13.3.2 — Mensajes firmados con WS-Security (CWE-345)

> *"Verifique que el payload del mensaje está firmada mediante WS-Security para garantizar un transporte fiable entre el cliente y el servicio."*

**Explicación:** WS-Security firma los mensajes SOAP: ni el contenido ni el remitente pueden falsificarse, incluso si el transporte se compromete. **Niveles: L1, L2.**

> *Nota: debido a los problemas con los ataques XXE contra los DTD, la validación DTD no se debe utilizar y debe deshabilitarse la evaluación DTD del framework, según los requisitos de configuración del capítulo V14.*

## V13.4 GraphQL

### 13.4.1 — Protección contra consultas costosas (CWE-770)

> *"Verifique que se utiliza una lista de permisos de consulta o una combinación de limitación de profundidad y limitación de cantidad para evitar que GraphQL o la expresión de la capa de datos provoque una denegación de servicio (DoS) como resultado de costosas consultas anidadas. Para escenarios más avanzados, se debe usar el análisis de costos de consulta."*

**Explicación:** una sola consulta GraphQL puede anidar miles de objetos y tumbar la base de datos: listas de consultas permitidas, límites de profundidad/cantidad o análisis de costos lo impiden. **Niveles: L1, L2.**

### 13.4.2 — Autorización en la capa de negocio (CWE-285)

> *"Verifique que GraphQL u otra lógica de autorización de capa de datos podría implementarse en la capa de lógica de negocio en lugar de la capa GraphQL."*

**Explicación:** la autorización no vive en el "resolver" superficial: se aplica en la lógica de negocio, donde se conoce el contexto y no se puede saltar. **Niveles: L1, L2.**

## Resumen

> V13 asegura las APIs: un único parsing coherente, nada de secretos en
> URLs, autorización en capas, validación de esquemas (JSON y XSD),
> métodos HTTP restringidos, protección CSRF, mensajes íntegros en
> tránsito y GraphQL blindado contra consultas costosas.
